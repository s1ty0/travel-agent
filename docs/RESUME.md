# 简历项目与面试说明

项目名称：**行迹：多Agent旅游规划助手**。

## 简历版本

**项目介绍：** 一款面向自由行用户的 **AI 旅游规划网站**。用户用自然语言描述目的地、预算和偏好，生成包含**景点、用餐与步行安排**的逐日行程，支持**来源追溯、局部修改、历史版本与导出**。目前公网覆盖杭州西湖东岸与苏州古城，使用真实地图数据，营业、预约与价格明确标注待核实。

**技术栈：** Next.js、React、TypeScript、FastAPI、Pydantic、PostgreSQL、DeepSeek、OpenStreetMap、Playwright、GitHub Actions。

**核心亮点：** 设计**景点与餐饮双Agent并行研究**，模型从实际来源中选择地点，由程序完成**时间窗、交通衔接与逐日覆盖校验**；基于 **PostgreSQL事务锁与幂等键**实现任务原子创建和独占认领，支持进度、取消与版本保留，避免重复提交触发重复规划；通过**共享费用账本、三层试用限额与用户Key加密存储**约束服务消耗，并完成 Vercel 前后端、持久数据库及真实浏览器流程的上线验证。

**在线体验：** [https://travel-agent-web-tau.vercel.app](https://travel-agent-web-tau.vercel.app)

多Agent为自建固定分支汇合，标准联合研究仍为默认策略，专精并行可切换。没有使用 LangGraph 或 RAG 向量库，不写未实现的商业接口。

项目链接：[代码仓库](https://github.com/s1ty0/travel-agent)、[架构](ARCHITECTURE.md)、[演示](DEMO.md)、[评测](EVALUATION_REPORT.md)。实测数字必须保留样本量、真实/合成边界；不写“准确率100%”“稳定提升XX%”或“已服务大量用户”。

## 面试如何讲

**为什么多个Agent？** 体验与餐饮可以并行，输出通过ID合并，权限和预算由同一个程序控制。三例对照显示专精成本更高，尚不足以改成默认；因此保留联合默认和可切换实验，不以Agent数量作为成果。

**为什么不用模型直接排完？** 名称、精确时间和价格容易失真。模型负责候选取舍；地点只从实际来源解析，交通用精确端点，时间/数量/禁去/逐日由程序检查。未知路线不能自动判通过，仍可交付有缺口的草案。

**如何避免重复收费？** 请求与任务创建、worker认领分别事务化；同ID不同内容拒绝，删除后保留墓碑；失联任务不自动重放。供应商调用本身不具备统一幂等保证，因此不能宣称“所有外部调用恰好一次”。

**5元是否绝对账单封顶？** 不是。程序按已知价格高价估算并原子预留，未知用量停止且保留未结算金额；供应商实际账单仍需对账。高德依赖账号免费且没有付费回退，不由程序代改套餐。

**修改为什么可控？** 识别明确日期、结束时间、步行上限、排除来源ID及预算；只重排涉及日期。证据复用不代表新路线已知，删点后新相邻端点需要补查。当前“换掉”仅移除并要求另选，不能夸成任意智能替换。

**失败学到了什么？** 初期5次来源额度不足以同时查多天地点、餐厅和路线，且模型交替查询可能耗尽最终提交机会。后续改为来源先行、有限研究和程序排程；修复高德限速竞争、Windows孙进程泄漏、未知路线当零步行、长HTTP缺进度误触租约、重研究带回禁去地点等问题。具体失败可查开发日志。

**下一步是什么？** 扩大带人工核查的真实旅行评测；补周边城市候选、交通酒店授权、正式身份和运维。购买审批目前是边界设计，没有真实交易工具；不能展示为已实现的自动购票闭环。

## 诚实口径

当前已部署限定城区的公网真实规划版，模型和搜索实时请求 DeepSeek，地图来自2026-11-11真实 OSM 数据快照。测试和本机仍可显式使用合成数据，公网禁止。没有确认小红书/美团全量搜索授权，没有实时票务酒店库存，没有注册账户或跨设备恢复，没有用户省时数据。AI辅助开发应按面试要求说明，展示自己能解释、复现和修改代码的证据。上线验收通过不等于不存在缺陷，具体证据与未完成范围见[发布记录](devlogs/2026-11-11-public-live-release.md)。
