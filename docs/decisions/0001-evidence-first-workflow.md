# ADR-0001：采用证据驱动的受控工作流

日期：2026-11-08

状态：暂定；M1～M3 验证后可替代。

依据：[用户需求长期记忆](../../AGENT.md)、[首轮调研](../research/2026-11-08-landscape.md)。

ADR 是架构决定记录，用来保留“选了什么、为什么、怎样验证”。

## 问题

用户需要节省跨平台做攻略的时间，同时希望多 Agent 提效、结果可信，并在购买等操作前审批。

主要风险来自事实过期、来源缺失、预算口径不明、路线不可行和交易重复执行。单纯增加角色或要求模型“检查一下”不能可靠解决这些问题。

## 暂定决定

1. **任务分工，平台共享。** 按目的地、体验、交通住宿与行程任务组织 Agent。小红书等平台实现为独立适配器，避免每个 Agent 各自登录、检索和重复计费。
2. **证据先于结论。** 候选、主张和来源独立保存。平台总结保留派生关系，关键事实按主张类型核对原始或权威来源。
3. **程序检查硬约束。** 模型理解和解释，程序负责金额、时间、权限和状态。未知条件单独返回，不自动通过。
4. **先做只读闭环。** MVP 规划、修改、导出与官方跳转；真实库存、订单、支付后续接入。
5. **审批由服务端执行。** 交易参数、报价、用户和有效期绑定审批。恢复、重试及参数变化不能绕开校验。
6. **编排优先验证 LangGraph。** 它有公开的中断与持久化能力；Google ADK 作为可行备选。框架可替换，领域对象和工具契约不依赖其内部类型。
7. **先轻存储、后按需要扩展。** 结构化数据、事件和检查点起步；暂不引入向量库、微服务集群或多套 Agent 框架。

## 考虑过的替代方案

| 方案 | 优点 | 本阶段不作为主路线的原因 |
| --- | --- | --- |
| 单 Agent + 工具 | 开发和排障简单；适合作为基线。 | 保留并先实现；是否足够由后续对照实验决定。 |
| 每个平台一个 Agent | 容易把平台名映射到角色。 | 容易重复检索、混淆证据和接口边界；确有平台专项价值时仍可局部使用。 |
| 多 Agent 自由聊天达成共识 | 原型直观。 | 执行路径、循环成本和共享事实难控制；共识不等于独立证据。 |
| 直接复制旅行 Demo | 能快速展示生成行程。 | 国内数据源、权限、引用和交易约束仍需重做；旧样例还可能已迁移。 |
| Google ADK 主框架 | 有明确的角色、并行和多模型能力。 | 可行备选；先用同一国内模型和恢复样例验证，再决定是否替代 LangGraph。 |

## 代价

- 要设计证据、费用、校验、版本和审批对象，早期比纯聊天原型工作更多。
- 部分平台暂时接不进来，首版可能依赖公开检索、地图和用户主动导入。
- 确定性校验只能覆盖已经编码且有输入数据的规则；未覆盖或未知条件必须可见。
- Agent 并行会增加配额竞争和汇合处理，必须与单 Agent 和普通并行工具分别比较。

## 验证与推翻条件

- M2 完成真实只读检索、证据归档及单 Agent 基线。
- M3 验证并行、检查点恢复、失败处理、成本与质量；不能只用角色数量验收。
- 若多 Agent 没有测得收益，合并角色；若 LangGraph 与选定模型/恢复需求不兼容，以新 ADR 替代。
- 若拿不到某平台权限，替换适配器或降级，不改变可信、预算和审批要求。
- 交易开放前，审批过期、参数变化、跨用户复用、重放及未知订单状态测试必须通过。

## 依据边界

LangGraph 的 [中断](https://docs.langchain.com/oss/python/langgraph/interrupts) 和 [持久化](https://docs.langchain.com/oss/python/langgraph/persistence) 是框架能力依据。Google ADK 的 [并行工作流](https://adk.dev/agents/workflow-agents/parallel-agents/) 是备选依据。它们均不证明本项目已经实现或正确配置这些能力。
